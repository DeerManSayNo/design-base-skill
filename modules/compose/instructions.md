# 组件审查与实现

## 职责与输入

依据项目规范、Token 与契约审查并实现组件或页面。缺少关键依据，或共享设计决定与适用范围变化时进入 foundation 准入；机械修复只验影响，不得静默放宽规范使组件通过。

## 页面与任务组织

采用已有页面模式时核对任务、密度和导航上下文；信息关系或方向尚未解决时读取 [设计推导](../../references/design-reasoning.md)。需要自行决定新视觉、重做大面积页面，或用户要求避免 AI 味与模板感时，再读取 [审美防偏](../../references/anti-ai-aesthetic.md)。局部修正沿用既有关系，不为填充版面引入没有任务、状态或品牌依据的装饰。

## 候选审查

通过现有目录、导出、代码搜索和 Stories 定位候选，按本次用途检查，不额外整理目录。

从当前页面向周边组件、共享导出、包装层、运行示例及代表性调用方检索，检查实际源码。围绕任务核对：

- 用途、业务语义、结构和组合方式是否匹配。
- Token、主题模式、排版、间距、尺寸、布局、图标、圆角和阴影是否符合相关子系统。
- 变体及加载、禁用、焦点、选中、错误等适用状态是否完整。
- 指针、键盘、触摸、焦点、可访问名称及动态效果是否符合交互契约。
- API 是否能自然表达差异，样式覆盖和改造是否影响现有调用方。

## 决策

| 结论 | 条件 | 动作 |
| --- | --- | --- |
| 复用 | 满足任务和相关设计契约 | 直接使用既有公开接口 |
| 改造 | 核心语义一致，能在合理边界内达到合规，影响可控 | 补齐变体、状态或实现，同步调用方 |
| 构建 | 语义不符、无法合理改造成合规实现，或改造造成 API 污染 | 依据项目 Token 和契约构建 |

外部组件可通过适配层实现合规，仍需接受同一审查。高度业务化且没有稳定复用边界的实现留在业务层。新建前检查命名和资产归属，说明与旧实现的替代或共存关系，避免产生无说明的重复组件。

## 实施与交接

1. 简述候选、决定及依据；修改共享默认、Token 消费或 API 前核对引用、包装层和覆盖。
2. 通用视觉和交互放入组件，场景差异用明确接口表达，数据请求与业务编排留在业务层。优先沿用项目框架、组件库和可靠的交互原语。
3. 已有测试或示例受影响时同步更新；缺少时按风险补充必要验证，不要求每个组件配齐文档和展示页。有示例时与业务共用组件、主题、字体和必要 Provider，采用模拟数据覆盖关键状态。
4. 同步类型、导出、调用方、用法和入口；设计规则发生变化先经 foundation 确认。
5. 将变更文件、使用的 Token、相关契约、影响范围、示例及待验证项交给 verify。发现与任务无关的历史问题单独记录，不扩大重构。
