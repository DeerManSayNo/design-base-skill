# 建立与演进项目设计系统

## 职责与输入

维护项目设计依据、Token 和各子系统契约。读取调度层给出的任务范围与项目入口，按入口的追加条件读取参考。已有资料足够时直接采用。

## 执行

沿用已确认方向时只补本次缺口；自拟或重选方向读取 [设计推导](../../references/design-reasoning.md) 与 [审美防偏](../../references/anti-ai-aesthetic.md)。初始化或迁移单文件规范时读取 [项目模板](../../templates/README.md)，按其结构落地；已有等价结构不另建来源。占位符须替换或明确待确认。

1. 盘点已有产品信息、设计记录、Token、主题、组件规范，区分已确认规则、候选、历史偏差与局部例外。代码可作为提案依据，不自动升级为规范。
2. 初始化建立模板规定的独立文档与十三类系统索引，记录真实覆盖状态。首次维护单文件规范时将已有内容迁入对应模块、更新入口与引用，保持原设计决定及代码不变；缺失内容注明缺口。已有模块化项目仅处理本次缺口，不重做完整覆盖检查。
3. 规则简记用途、当前约定与资产引用；复杂行为链接契约、源码和示例。当前不用的组件无需提前实现。
4. 定义或补齐 Token 契约，优先沿用项目格式、工具链和命名，不为统一形式引入第二套来源。
5. 按下节审查共享规则，已有授权内说明依据后推进，未解决的关键产品选择才请求确认；交由 verify 验证，采纳后同步资产。

## 共享规则准入

共享 Token、组件默认、文案/状态、模式及规范性示例的设计决定或适用范围变化时：

1. 按批次在已有资产记录产品依据、适用边界、代表场景和结论；模型/库默认、代码现状、示例与临时覆盖不能单独成为规范依据，不逐 Token 建审批表。
2. 沿默认值到消费场景检查装饰叠加、重复强调、意图外显和伪状态；疑点再读审美防偏，不以单个视觉元素判错。
3. 依据成立且通过 verify 共享专项才采纳；否则隔离为候选，不切换有效默认。例外须有明确授权、范围、风险和退出条件，不能记作验证通过。

普通复用、纯链接/格式修复及已批准例外的原范围实施不重新准入；规则或范围变化才重审。示例须区分规范用法与探索展示。

## 存量演进

治理或升级时按上述准入标准抽查目标任务、共享默认与代表性组合，区分规则缺失、实现偏离及规则自身有问题；已有规范仍须接受审查，不因历史沿用免检。仅追溯本次范围，依据缺失记为未证实，不直接判失败。先处理任务阻碍，再按使用频率、共享影响和风险迁移；无使用证据时注明依据，不虚构数据。

沿用健康部分，先在代表性场景验证新规则，再扩大范围。分批迁移只记录目标规则、本次范围、保留例外及退出条件、剩余范围；移除旧实现前核对消费者，风险较大的共享变化保留可恢复路径。局部任务发现无关问题时简记，不启动全项目治理。

## Token 契约

- 基础层保存原始色板、尺寸刻度等值；语义层表达文字、表面、动作、状态等用途；组件层按实际需要表达组件决策，避免机械复制所有属性。
- 主题或模式通过映射复用语义，避免为每个模式复制独立组件体系。组件优先消费语义或组件 Token；基础值直用及必要硬编码需有明确范围和依据。
- 明确名称、类型、值或别名、用途、适用模式及来源；别名应可解析、类型兼容且无循环，必要模式完整。具体值保持单一权威来源，生成代码不手工维护。
- 采用现有结构化格式与解析器；新建交换格式时优先评估 DTCG，核对实际工具支持。Token 导出、CSS 变量和平台映射应可追溯。

## 输出与边界

向 compose 或 verify 提供有效规则、Token 与子系统路径、变化范围及待确认项。待验证候选注明状态、代表场景和隔离方式；compose 可在限定场景实现验证，通过前不切换有效默认。设计值落到 Token，行为落到契约；不把所有规则强行编码成 Token，不扩展为无关组件重写。
